# Message API Contracts

## 1. Overview

This document defines the message contracts used for communication between autonomous agents through the Cross-Network A2A Gateway.

The purpose of message contracts is to ensure:

- Structured communication
- Agent interoperability
- Secure message exchange
- Clear intent handling
- Easy debugging

All agent communication follows JSON-based messages.

---

# 2. Message Architecture

Communication flow:


Agent

|

Create Message

|

A2A Gateway

|

Validate

|

Route

|

Receiver Agent


---

# 3. Base Message Structure

Every A2A message follows a common format.

```json
{
  "message_id": "msg-001",

  "message_type": "TASK_REQUEST",

  "version": "1.0",

  "timestamp": "2026-07-24T10:00:00Z",

  "sender": {
    "agent_id": "pm-agent",
    "organization": "SoftwareCompany"
  },

  "receiver": {
    "agent_id": "ba-agent",
    "organization": "SoftwareCompany"
  },

  "intent": "ANALYZE_REQUIREMENT",

  "payload": {},

  "security": {
    "token": "jwt-token"
  },

  "status": "SENT"
}
4. Message Types

The PoC supports the following message types:

Message Type	Purpose
AGENT_REGISTER	Register agent
PROJECT_REQUEST	Submit project request
TASK_REQUEST	Request another agent to perform task
TASK_RESPONSE	Return task result
CLARIFICATION_REQUEST	Request missing information
CLARIFICATION_RESPONSE	Provide requested information
PROPOSAL_REQUEST	Generate proposal
PROJECT_PROPOSAL	Send completed proposal
APPROVAL_REQUEST	Request approval
APPROVAL_RESPONSE	Return approval status
ERROR_MESSAGE	Report failure
5. Agent Registration Message
Purpose

Used when an agent joins the A2A network.

Example:

{
 "message_type":"AGENT_REGISTER",

 "payload":
 {
   "agent_id":"technical-agent",

   "organization":
   "SoftwareCompany",

   "role":
   "Solution Architect",

   "capabilities":
   [
     "architecture_design",
     "technology_selection"
   ]
 }
}
6. Project Request Message

Receiver

   "Healthcare Platform",

   "description":

   [
    "Manage appointments",

   ],

   "expected_timeline":
   "6 months"
 }
}
7. Task Request Message
Purpose

Allows one agent to request another agent to perform a task.

Example:

{
 "message_type":"TASK_REQUEST",

 "sender":
 {
  "agent_id":
  "pm-agent"
 },

 "receiver":
 {
  "agent_id":
  "technical-agent"
 },

 "payload":
 {
  "task":
  "DESIGN_ARCHITECTURE",

  "context":
  {
    "requirements":
    [
     "Patient management",
     "Mobile application"
    ]
  }
 }
}
8. Task Response Message

Used by agents to return results.

Example:

{
 "message_type":
 "TASK_RESPONSE",

 "sender":
 {
  "agent_id":
  "technical-agent"
 },

 "payload":
 {
  "result":
  {
   "architecture":
   "Microservices",

   "technology_stack":
   [
    "FastAPI",
    "PostgreSQL"
   ]
  },

  "confidence":
  0.87
 }
}
9. Clarification Request Message
Purpose

Used when information is missing.

Example:

{
 "message_type":
 "CLARIFICATION_REQUEST",

 "payload":
 {
  "question":
  "How many users are expected?",

  "reason":
  "Required for infrastructure estimation"
 }
}
10. Clarification Response Message

Example:

{
 "message_type":
 "CLARIFICATION_RESPONSE",

 "payload":
 {
  "answer":
  "Approximately 10000 users"
 }
}

14. Message Lifecycle

Every message follows:

CREATED

   |

SENT

   |

RECEIVED

   |

PROCESSING

   |

COMPLETED

   |

FAILED (if error)

2. Sender identity

3. JWT token

4. Receiver availability

5. Permission
