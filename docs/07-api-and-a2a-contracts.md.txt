# API and A2A Communication Contracts

## 1. Overview

This document defines the communication contracts between all components of the autonomous chatbot system.

The architecture uses REST APIs with JSON payloads.

Communication flow:

```text
Client

↓

Client Backend

↓

Client Agent

↓

A2A Gateway

↓

Project Manager Agent

↓

Specialist Agents
```

The A2A Gateway is the only communication bridge between the Client Network and Company Network.

---

# 2. Communication Principles

## 2.1 No Direct Communication

The following communication is NOT allowed:

```text
Client Agent

X

Technical Agent
```

or

```text
Client

X

PM Agent
```

All requests must go through:

```text
Client Agent

↓

A2A Gateway

↓

PM Agent
```

---

## 2.2 Message Structure

Every A2A message follows a common structure.

```json
{
  "message_id": "uuid",
  "conversation_id": "uuid",
  "project_id": "uuid",
  "sender": "client_agent",
  "receiver": "pm_agent",
  "message_type": "PROJECT_REQUEST",
  "timestamp": "2026-07-29T10:00:00",
  "payload": {}
}
```

# 6. Gateway Responsibilities

The Gateway performs:

## Authentication

Validate JWT token.

---

## Authorization

Verify:

```
Client Agent

is allowed to communicate with

PM Agent
```

---

## Validation

Check:

- Message format
- Required fields
- Sender identity

---

## Routing

Forward message.

---

## Logging

Store:

```
gateway_logs
```

# 12. Client Agent Answer Decision

The Client Agent processes the question.

```text
Receive Question

↓

Search Memory

↓

Search pgvector

↓

Answer Exists?

       │

 YES───┴───NO

 │          │

 ▼          ▼

Reply      Ask Client
```

---

## If Answer Exists

Response:

```json
{
  "message_type":
  "CLARIFICATION_RESPONSE",

  "answer":
  "Yes, GPS tracking is required."
}
```

---

## If Answer Does Not Exist

Client Agent asks:

```text
Would you like delivery partners to have GPS tracking?
```

# 19. Message Types

Supported A2A messages:

| Message Type | Purpose |
|---|---|
| PROJECT_REQUEST | Initial requirement transfer |
| TASK_REQUEST | Assign work to agent |
| TASK_RESPONSE | Agent result |
| CLARIFICATION_REQUEST | Ask missing information |
| CLARIFICATION_RESPONSE | Provide information |
| SUMMARY | Requirement summary |
| APPROVAL_REQUEST | Request approval |
| APPROVAL_RESPONSE | Approval result |
| PROPOSAL | Final proposal |

---

# 20. Error Handling

Every response should contain:

```json
{
  "status":
  "SUCCESS",

  "error":
  null
}
```

Failure example:

```json
{
  "status":
  "FAILED",

  "error":
  "Agent timeout"
}
```

---

# 21. API Design Principles

- REST-based communication
- JSON-only messages
- Stateless gateway
- Persistent message logging
- Clear agent ownership
- No direct agent access
- Every action traceable through logs

---

# 22. Summary

The API architecture provides:

- Client chatbot communication
- Internal agent communication
- Secure A2A routing
- Task delegation
- Clarification handling
- Approval workflow
- Proposal generation

The contracts defined here are sufficient to implement the FastAPI backend for the PoC.
