# Memory Architecture and pgvector Design

## 1. Overview

Autonomous agents require memory to maintain context across conversations and tasks.

In this PoC, memory is divided into two layers:

1. Structured Memory
2. Semantic Memory

Structured memory is stored in PostgreSQL.

Semantic memory is stored using PostgreSQL's pgvector extension.

The purpose is not to store every conversation message as embeddings, but to store meaningful knowledge that helps agents reason better.

# 3. Memory Types

The system maintains four types of memory.

---

# 3.1 Conversation Memory

Stores active conversations.

Example:

```text
Client:

We want Stripe payment integration.

Client Agent:

Noted. I will include Stripe.
```

Stored in:

```
chat_messages
```

Purpose:

- Display chat history
- Maintain conversation continuity
- Audit communication

This data is NOT embedded.

---

# 3.2 Project Memory

Stores project-specific knowledge.

Examples:

```text
Project:

Food Delivery Application


Requirements:

Customer App

Restaurant Portal

Delivery Tracking
```

Stored in:

```
projects

project_requirements
```

---

# 3.3 Decision Memory

Stores important decisions made during discussions.

Examples:

```text
Decision:

Payment Gateway

Value:

Stripe


Decision:

Authentication

Value:

JWT
```

Stored in:

```
project_decisions
```

These are embedded into pgvector.

---

# 3.4 Agent Memory

Stores observations generated by agents.

Examples:

```text
Technical Agent:

The project requires real-time location tracking.

BA Agent:

Multiple user roles exist.
```

Stored in:

```
agent_memory
```

# 6. Why Use pgvector?

Traditional database search works using exact matching.

Example:

Search:

```
payment gateway
```

Finds:

```
payment gateway
```

But it may miss:

```
online payment provider
```

because the words are different.

Vector search understands meaning.

Example:

Query:

```
How should customers pay?
```

Can retrieve:

```
Stripe integration selected
```

because the meaning is similar.

# 7. pgvector Storage

The pgvector table stores embeddings.

```sql
knowledge_embeddings

id UUID PRIMARY KEY

project_id UUID

source_type VARCHAR

source_id UUID

content TEXT

created_at TIMESTAMP
```

---

## source_type

Examples:

```text
REQUIREMENT

DECISION

SUMMARY

ARCHITECTURE

PROPOSAL
```

# 8. Embedding Workflow

Whenever important information is created:

```text
New Information

↓

Evaluate Importance

↓

Create Text Chunk

↓

Generate Embedding

↓

Store Vector

↓

Save Metadata
```

---

Example:

Input:

```text
Client selected Stripe as payment provider.
```

↓

Embedding generated.

↓

Stored:

```text
content:

Client selected Stripe as payment provider.


vector:

[0.231,0.123,...]
```

### Proposal Summaries

### Client Preferences


---

# 10. What Should NOT Be Embedded?

Do not embed:

## Greetings

Example:

```
Hello

Thank you

Good morning
```

---

## Every Chat Message

Avoid:

```
Message 1

Message 2

Message 3
```

Thousands of irrelevant vectors reduce retrieval quality.

---

## Temporary Agent Thoughts

Do not store:

```
Maybe this approach works.
```

Only store finalized decisions.

# 22. Design Decisions

This PoC intentionally avoids:

- Separate vector databases
- Redis memory
- Knowledge graphs
- Complex RAG pipelines
- External memory services

The design uses:

- PostgreSQL for application state
- pgvector for semantic search
- Llama for reasoning

This provides enough capability to demonstrate autonomous agents while keeping the implementation achievable within one week.
