# Cross-Network Autonomous Agent-to-Agent (A2A) Chatbot PoC

## 1. Introduction

This project is a **Proof of Concept (PoC)** that demonstrates how autonomous AI agents belonging to independent organizations can collaborate through a secure Agent-to-Agent (A2A) communication layer while maintaining a chatbot-based user experience.

Unlike traditional chatbot systems where users directly interact with a single AI assistant, this PoC simulates two independent organizations:

- Client Organization
- Software Development Company

Each organization owns its own AI agents and infrastructure.

The Client never communicates directly with the Software Company.

Instead, communication occurs through autonomous AI agents connected via an A2A Gateway.

The goal is to demonstrate that independent AI agents can:

- Understand business requirements
- Plan tasks
- Delegate work
- Communicate with other agents
- Maintain conversational memory
- Ask clarification questions
- Generate project proposals

while providing a seamless conversational experience.

---

# 2. Project Objective

Build a chatbot-driven autonomous agent system where:

- Client submits software requirements using a structured form.
- Client Agent reviews the submitted requirements.
- Client Agent starts a conversation with the client.
- Client Agent communicates with the Company Network.
- Project Manager Agent orchestrates requirement analysis.
- Specialist agents independently analyze different aspects.
- Agents collaborate through A2A communication.
- Missing information is requested through conversational follow-up.
- Project Manager approves the final requirement summary.
- Client reviews and approves the summary.
- Final proposal is generated.

The entire process should appear as a natural conversation instead of a traditional workflow engine.

# 5. Chatbot-Based Architecture

Instead of exposing every autonomous agent to the user, this PoC presents only two chatbot interfaces.

## Chatbot 1

Client ↔ Client Agent

Visible to the user.

Purpose:

- Requirement discussion
- Requirement validation
- Clarification
- Updates
- Final review

---

## Chatbot 2

Client Agent ↔ Project Manager Agent

Internal.

Purpose:

- Requirement analysis
- Agent collaboration
- Task delegation
- Missing information requests
- Proposal generation

This chatbot is never visible to the client.

# 6. Complete Workflow

## Step 1

Client logs into the application.

↓

Client creates a new project.

↓

Client fills the requirement form.

Example:

- Project Name
- Description
- Target Platforms
- Target Audience
- Timeline
- Budget
- Key Features
- Third-party Integrations

↓

Client clicks Submit.

---

## Step 2

Project requirements are stored inside PostgreSQL.

A new project is created.

A new chat session is created.

Client is redirected to the Client Chat page.

---

## Step 3

Client Agent automatically begins processing.

The Client Agent:

- Reads the submitted requirements.
- Retrieves project context.
- Uses the Llama model to analyze the requirements.
- Identifies missing information.
- Generates an initial conversation.

Example:

"Hi John,

I've reviewed your project requirements.

Your project appears to be an e-commerce platform targeting Android and iOS users.

I noticed that payment gateway information is missing.

Do you already have a preferred payment provider?"

---

## Step 4

If the client responds:

The Client Agent:

- Stores the response.
- Updates project memory.
- Updates semantic memory if necessary.
- Determines whether enough information exists.

If additional information is still required:

Continue chatting.

Otherwise:

Forward the request to the Company Network.

---

## Step 5

The Client Agent sends an A2A request.

```

Client Agent

↓

A2A Gateway

↓

Project Manager Agent

```

The message contains:

- Requirement summary
- Requirement details
- Chat summary
- Missing assumptions
- Project metadata

---

## Step 6

Project Manager Agent receives the request.

The PM Agent:

- Creates an execution plan.
- Creates agent tasks.
- Delegates work.

Example:

Requirement Analysis

↓

Business Analyst

Architecture Design

↓

Technical Agent

Cost Estimation

↓

Cost Agent

Timeline

↓

Timeline Agent

Risk Analysis

↓

Risk Agent

---

## Step 7

Each specialist agent independently reasons using Llama.

Every agent:

- Reads assigned task.
- Retrieves project memory.
- Generates analysis.
- Stores results.
- Returns response.

Agents never communicate directly with the client.

---

## Step 8

Project Manager collects all responses.

PM evaluates:

- Missing information
- Contradictions
- Risks
- Suggestions

If clarification is required:

PM sends a clarification request.

---

## Step 9

Clarification Flow

```

PM Agent

↓

Gateway

↓

Client Agent

↓

Can Client Agent Answer?

↓

YES → Reply immediately

↓

NO

↓

Ask Client

↓

Client replies

↓

Client Agent updates memory

↓

Gateway

↓

PM Agent

```

This clarification loop continues until all required information has been collected.

---

## Step 10

Project Manager generates a consolidated requirement summary.

The summary includes:

- Project overview
- Functional requirements
- Technical recommendations
- Estimated cost
- Timeline
- Risks
- Assumptions

The PM manually reviews the summary.

Once approved:

Summary is sent back.

---

## Step 11

Client Agent receives the summary.

The Client Agent presents it inside the client chat.

Example:

"I've received the finalized requirement summary from our project team.

Please review it carefully.

If everything looks correct, you can approve it.

Otherwise, let me know what you'd like to modify."

---

## Step 12

Client reviews.

If changes are requested:

Repeat clarification workflow.

If approved:

Project status becomes:

APPROVED

---

## Step 13

Proposal Generation

Project Manager generates:

- Scope
- Deliverables
- Timeline
- Cost
- Technology Stack
- Assumptions
- Risks

Proposal is stored.

Proposal becomes available for download.

# 8. Development Principles

This project is intentionally designed as a lightweight PoC.

Guidelines:

- Keep the architecture simple.
- Use PostgreSQL for all transactional data.
- Use pgvector only for semantic retrieval.
- Use Llama for reasoning.
- Avoid enterprise-level complexity.
- Prefer readability over optimization.
- Build for demonstration rather than production.
